1. INTRODUCCIÓN Y CONCEPTOS
═══════════════════════════════════════════════════════════════════════════════════════════════════════

¿QUÉ ES UN CRM?
───────────────
CRM = Customer Relationship Management (Gestión de Relaciones con Clientes)

En realidad, un CRM es más que eso. Es un sistema que centraliza:
• Información de clientes
• Información de empleados
• Procesos de negocio
• Historial de transacciones
• Comunicaciones
• Reportes y análisis

TIPOS DE CRM
────────────
1. OPERACIONAL (el nuestro para Plus Móvil)
   → Gestiona operaciones diarias
   → Ejemplo: registro de servicios, asignación de tareas, turnos
   
2. ANALÍTICO
   → Análisis de datos históricos
   → Ejemplo: dashboard, predicciones, tendencias
   
3. COLABORATIVO
   → Comunicación entre departamentos
   → Ejemplo: notas compartidas, actualizaciones en tiempo real

CARACTERÍSTICAS CLAVE DE UN BUEN CRM
────────────────────────────────────
✓ Automatización (reducir trabajo manual)
✓ Centralización (un solo lugar para todos los datos)
✓ Escalabilidad (crecer sin problemas)
✓ Seguridad (proteger datos sensibles)
✓ Usabilidad (fácil de usar)
✓ Integración (conectar con otras herramientas)
✓ Reportes (datos claros y accionables)

2. ANÁLISIS DE REQUISITOS (CÓMO EMPEZAR)
═══════════════════════════════════════════════════════════════════════════════════════════════════════

Antes de escribir una sola línea de código, debes entender el negocio.

PREGUNTAS CLAVE A HACER
───────────────────────

A. INFORMACIÓN GENERAL
□ ¿Cuál es el negocio exactamente?
□ ¿Cuántas personas trabajan?
□ ¿Cuántos clientes/usuarios tiene?
□ ¿Crecimiento estimado en 1 año? ¿En 5 años?
□ ¿Presupuesto para el desarrollo?
□ ¿Plazo de entrega?

B. PROCESOS ACTUALES
□ ¿Cómo trabajan ahora? (manual, Excel, WhatsApp, etc.)
□ ¿Qué duele más del sistema actual?
□ ¿Cuáles son los pasos del proceso principal?
□ ¿Qué datos se pierden o generan errores?
□ ¿Cuántas transacciones/servicios por día?

C. USUARIOS Y ROLES
□ ¿Cuántos tipos de usuarios hay?
□ ¿Qué hace cada uno?
□ ¿Qué información necesita cada uno?
□ ¿Quién puede editar/borrar datos?
□ ¿Quién solo puede ver datos?

D. DATOS QUE SE NECESITAN REGISTRAR
□ ¿Qué información de clientes es esencial?
□ ¿Qué información de empleados?
□ ¿Qué información de transacciones/servicios?
□ ¿Histórico cuánto tiempo hay que guardar?
□ ¿Informes/reportes que necesitan?

E. INTEGRACIÓN CON OTRAS HERRAMIENTAS
□ ¿Tienen WhatsApp? ¿Instagram? ¿Email?
□ ¿Usan Google Drive o algún cloud?
□ ¿Necesitan conectar con banco/pasarela de pagos?
□ ¿Necesitan GPS/mapas?
□ ¿Necesitan enviar notificaciones?

F. ESPECIFICIDADES DEL NEGOCIO
□ ¿Hay horarios especiales? ¿Turnos?
□ ¿Hay conceptos de dinero (cobros, pagos)?
□ ¿Hay documentos que vencer?
□ ¿Hay múltiples locaciones/sedes?
□ ¿Hay temporadas (picos de demanda)?

EJEMPLO 1: CLIENTE SOLICITA SERVICIO
──────────────────────────────────────
Nombre: Cliente solicita línea móvil

Actores:
• Cliente (envía WhatsApp)
• Operadora (recibe y asigna)
• Chofer (entrega)

Precondiciones:
□ Cliente tiene número de WhatsApp de la empresa
□ Operadora está en turno
□ Hay móviles disponibles

Flujo principal:
1. Cliente envía mensaje: "Necesito móvil para barrio X, familia Pérez"
2. Cliente envía ubicación GPS
3. Sistema captura: número, hora, mensaje, GPS
4. Operadora ve el mensaje en su panel
5. Operadora crea servicio: cliente, destino, hora estimada
6. Operadora ve móviles disponibles en estado real
7. Operadora asigna móvil XYZ al servicio
8. Operadora envía mensaje rápido: "Móvil 205 llega en 10 minutos"
9. Sistema registra: hora de respuesta (calcula tiempo)
10. Chofer recibe info por Zello, va al destino
11. Chofer llega, cliente recibe servicio
12. Operadora marca servicio como "entregado"
13. Sistema registra automáticamente: hora de entrega, duración

Flujo alternativo A: No hay móviles disponibles
→ En paso 6, operadora ve que NO hay disponibles
→ Operadora envía: "No contamos con servicio disponible en este momento"
→ Servicio se marca como "cancelado"
→ Sistema registra el rechazo

Flujo alternativo B: Chofer no encuentra al cliente
→ Chofer reporta por Zello: "No encuentro al cliente"
→ Operadora avisa al cliente por WhatsApp
→ Si cliente no responde 3 intentos, servicio = "no entregado"
→ Sistema registra incidente

Postcondiciones:
✓ Servicio registrado con todos los datos
✓ Tiempo de respuesta calculado
✓ Datos disponibles para reportes
✓ Cliente tiene historial de este servicio

EJEMPLO 2: OPERADORA CIERRA TURNO
──────────────────────────────────
Nombre: Operadora finaliza turno

Actores:
• Operadora
• Sistema (genera reporte)
• Contadora (recibe datos)

Precondiciones:
□ Operadora está en turno
□ Turno llegó a la hora de fin
□ Todos los servicios fueron cerrados

Flujo principal:
1. Operadora hace clic en "Cerrar Turno"
2. Sistema muestra checklist:
   ✓ ¿Confirmaste todas las asistencias?
   ✓ ¿Registraste todos los cobros?
   ✓ ¿Hay incidentes pendientes?
3. Operadora completa checklist
4. Sistema genera automáticamente:
   • Resumen: llamadas recibidas, atendidas, rechazadas
   • Tabla de cobros: móvil, concepto, monto
   • Asistencias: móviles que registraron la hora
   • Incidentes: fallas, retrasos, etc.
5. Sistema crea documento PDF descargable
6. Datos se sincronizan a la contadora automáticamente
7. Turno se marca como "cerrado"

Flujo alternativo: Hay servicios sin cerrar
→ Sistema avisa: "Hay 3 servicios abiertos"
→ Operadora debe cerrarlos primero

Postcondiciones:
✓ Turno cerrado y archivado
✓ Reporte generado y descargable
✓ Datos en Supabase para análisis
✓ Contadora puede ver los cobros

EJEMPLO 3: CONTADORA REVISA COBROS DEL MES
────────────────────────────────────────────
Nombre: Contadora genera reporte mensual

Actores:
• Contadora
• Sistema (busca y agrupa datos)

Precondiciones:
□ Mes ya finalizó
□ Hay datos de múltiples turnos

Flujo principal:
1. Contadora va a "Reportes" → "Por Período"
2. Selecciona: Mes, Año
3. Sistema busca en Supabase todos los turnos de ese mes
4. Sistema agrupa por:
   • Operadora
   • Concepto de cobro
   • Móvil
5. Sistema genera tabla:
   | Operadora | Llamadas | Atendidas | Cobros | Promedio |
   | --------- | -------- | --------- | ------ | -------- |
   | Ana       | 450      | 280       | 1200Bs | 4.28Bs   |
   | ...       | ...      | ...       | ...    | ...      |
6. Contadora ve gráficas de tendencias
7. Contadora exporta a Excel o PDF
8. Contadora archiva para auditoría

Postcondiciones:
✓ Reporte generado
✓ Datos validados
✓ Exportable
✓ Historiales para comparativa futura

CAPAS FUNCIONALES
─────────────────

1. CAPA DE PRESENTACIÓN (Frontend)
   ├── Páginas (Login, Dashboard, Reportes)
   ├── Componentes (Tablas, Formularios, Gráficas)
   ├── Hooks (Gestión de estado local)
   └── Utilidades (Formato, cálculos, helpers)

2. CAPA DE NEGOCIO (Backend)
   ├── Controllers (Lógica principal)
   ├── Services (Operaciones complejas)
   ├── Validadores (Datos correctos)
   └── Middleware (Auth, logging, CORS)

3. CAPA DE DATOS (Base de datos)
   ├── Usuarios y roles
   ├── Clientes y contactos
   ├── Transacciones/Servicios
   ├── Empleados/Choferes
   └── Configuración del sistema

4. CAPA DE INTEGRACIÓN (Externos)
   ├── WhatsApp API
   ├── Mapas/Geolocalización
   ├── Notificaciones
   └── Pagos (si aplica)

PATRONES DE ARQUITECTURA
────────────────────────

MVC (Model-View-Controller)
├── Model: Base de datos
├── View: Frontend
└── Controller: Backend

MVT (Model-View-Template)
├── Model: Base de datos
├── View: Frontend
└── Template: Backend

API REST
├── Frontend → API → Backend → DB
├── Cada endpoint hace una cosa específica
└── GET, POST, PUT, DELETE

MVVM (Model-View-ViewModel)
├── Model: Datos
├── View: UI
└── ViewModel: Lógica que conecta

PARA UN CRM TÍPICO: USA MVC + API REST
→ Es la más común, escalable y fácil de mantener

5. FLUJOS DE DATOS Y PROCESOS
═══════════════════════════════════════════════════════════════════════════════════════════════════════

FLUJO DE DATOS GENERAL EN UN CRM
────────────────────────────────

ENTRADA → PROCESAMIENTO → ALMACENAMIENTO → ANÁLISIS → SALIDA

1. ENTRADA
   ├── Formularios (usuario ingresa datos)
   ├── APIs externas (WhatsApp, Gmail, etc.)
   ├── Importación (CSV, Excel)
   └── Integración automática (webhooks)

2. PROCESAMIENTO
   ├── Validación (¿datos correctos?)
   ├── Transformación (formato correcto)
   ├── Lógica de negocio (¿qué hacer con esto?)
   └── Autorización (¿puede hacer esto?)

3. ALMACENAMIENTO
   ├── Guardar en base de datos
   ├── Crear historial/auditoría
   ├── Indexar para búsquedas rápidas
   └── Backup automático

4. ANÁLISIS
   ├── Cálculos de KPIs
   ├── Tendencias
   ├── Comparativas
   └── Alertas automáticas

5. SALIDA
   ├── Mostrar en dashboard
   ├── Generar reportes
   ├── Exportar (PDF, Excel)
   └── Notificaciones

CICLO COMPLETO DE UN REGISTRO
──────────────────────────────

1. CREACIÓN
   usuario crea → sistema valida → guarda en DB

2. LECTURA
   usuario pide datos → sistema busca en DB → muestra

3. ACTUALIZACIÓN
   usuario cambia dato → sistema valida → guarda cambio

4. ELIMINACIÓN (o archivo)
   usuario elimina → sistema marca como inactivo → guarda

5. ANÁLISIS
   sistema agrega datos → calcula métricas → genera reporte

6. STACK TECNOLÓGICO (QUÉ ELEGIR Y POR QUÉ)
═══════════════════════════════════════════════════════════════════════════════════════════════════════

DECISIONES CLAVE
────────────────

1. FRONTEND: ¿React, Vue o Angular?

   REACT
   ✓ Popular, mucha documentación
   ✓ Flexible, componentes reutilizables
   ✓ Vite para desarrollo rápido
   ✗ Curva de aprendizaje
   → MEJOR PARA: Equipos con experiencia, proyectos complejos

   VUE
   ✓ Más fácil de aprender
   ✓ Documentación excelente
   ✓ Rápido de prototipear
   ✗ Menos popular en grandes empresas
   → MEJOR PARA: Startups, equipo pequeño

   ANGULAR
   ✓ Framework completo (todo incluido)
   ✓ TypeScript nativo
   ✓ Escalable
   ✗ Más pesado, curva de aprendizaje
   → MEJOR PARA: Grandes proyectos empresariales

   NUESTRA RECOMENDACIÓN PARA Plus MÓVIL: React + Vite
   → Es el estándar actual, fácil de aprender, escalable

2. BACKEND: ¿Node, Python, Java o Go?

   NODE.JS (Express, Fastify)
   ✓ JavaScript en ambos lados (frontend + backend)
   ✓ Asincrónico (perfecto para I/O)
   ✓ npm ecosystem enorme
   ✓ Fácil de aprender
   ✗ Para cálculos pesados, no es ideal
   → MEJOR PARA: APIs, tiempo real, MVPs rápidos

   PYTHON (Django, FastAPI)
   ✓ Fácil de aprender
   ✓ Excelente para data science
   ✓ Comunidad grande
   ✗ Más lento que Node en I/O
   → MEJOR PARA: Análisis de datos, MVPs

   JAVA (Spring)
   ✓ Super escalable
   ✓ Usado en empresas grandes
   ✓ Performance
   ✗ Pesado, curva de aprendizaje
   → MEJOR PARA: Sistemas críticos, grandes volúmenes

   GO
   ✓ Super rápido
   ✓ Concurrencia excelente
   ✓ Eficiente
   ✗ Comunidad más pequeña
   → MEJOR PARA: Microservicios, sistemas de alto performance

   NUESTRA RECOMENDACIÓN PARA Plus MÓVIL: Node.js + Express
   → Es rápido prototipear, JavaScript en ambos lados, escalable

3. BASE DE DATOS: ¿SQL o NoSQL?

   SQL (PostgreSQL, MySQL)
   ✓ Relaciones entre tablas (clientes ↔ servicios)
   ✓ ACID (datos consistentes)
   ✓ Queries poderosos
   ✓ Mejor para datos estructurados
   ✗ Menos flexible para datos no estructurados
   → MEJOR PARA: CRM, sistemas financieros, datos relacionados

   NoSQL (MongoDB, Firebase)
   ✓ Flexible (documentos)
   ✓ Escalable horizontalmente
   ✓ JSON nativo
   ✗ Sin relaciones fuertes
   ✗ Más riesgo de inconsistencia
   → MEJOR PARA: Contenido, logs, datos sin estructura

   NUESTRA RECOMENDACIÓN PARA Plus MÓVIL: PostgreSQL (via Supabase)
   → Hay relaciones: clientes ↔ servicios, móviles ↔ asistencias
   → Necesitamos ACID (dinero/cobros, sin errores)
   → Plus: Supabase nos da PostgreSQL + auth + realtime

4. AUTENTICACIÓN: ¿Firebase, Supabase Auth, JWT Manual?

   FIREBASE AUTH
   ✓ Súper fácil, almacenado en la nube
   ✓ Múltiples métodos: email, Google, Apple
   ✓ Gratis hasta límite bueno
   ✗ Menos control
   → MEJOR PARA: Startups, desarrollo rápido

   SUPABASE AUTH
   ✓ Igual de fácil que Firebase
   ✓ Integrado con PostgreSQL
   ✓ Datos en tu control
   ✗ Menos integraciones sociales
   → MEJOR PARA: CRMs, datos privados

   JWT MANUAL
   ✓ Control total
   ✓ Sin dependencias externas
   ✗ Más código, más seguridad que manejar
   → MEJOR PARA: Empresas grandes con requisitos especiales

   NUESTRA RECOMENDACIÓN PARA Plus Móvil: Firebase Auth
   → Fácil implementar 3 roles diferentes
   → Integración probada con React
   → Gratuito

5. HOSTING: ¿Render, Vercel, Heroku, AWS?

   RENDER
   ✓ Fácil deploy, Next.js/Node
   ✓ $7/mes servidor
   ✓ Interfaz clara
   ✓ Conecta con DB fácil
   → MEJOR PARA: Startups, presupuesto limitado

   VERCEL
   ✓ Optimizado para Next.js
   ✓ Deployment automático desde Git
   ✗ Más caro
   → MEJOR PARA: Si usas Next.js

   HEROKU
   ✓ Súper fácil
   ✗ Cambió modelo gratuito
   ✗ Ahora es caro
   → NO RECOMENDADO actualmente

   AWS
   ✓ Cualquier cosa funciona
   ✓ Escalable infinitamente
   ✗ Caro si no sabes configurar
   ✗ Curva de aprendizaje
   → MEJOR PARA: Empresas grandes

   RAILWAY
   ✓ Parecido a Render, más moderno
   ✓ Integración de DB sencilla
   ✓ $5/mes mínimo

QUERIES TÍPICOS (SQL)
─────────────────────

-- Cuántos servicios atendió Ana hoy
SELECT COUNT(*) FROM servicios 
WHERE operadora_id = 'ana' AND DATE(fecha_hora) = TODAY()
AND estado = 'completado'

-- Cobros totales de hoy
SELECT SUM(monto) FROM cobros 
WHERE DATE(fecha_hora) = TODAY()

-- Documentos por vencer en 7 días
SELECT * FROM documentos 
WHERE fecha_vencimiento BETWEEN TODAY() AND TODAY() + INTERVAL 7 DAY
AND estado != 'vencido'

-- Clientes más frecuentes en el último mes
SELECT cliente_id, COUNT(*) as solicitudes 
FROM servicios 
WHERE fecha_hora > NOW() - INTERVAL 1 MONTH
GROUP BY cliente_id 
ORDER BY solicitudes DESC 
LIMIT 10

-- Zonas con más demanda
SELECT zona, COUNT(*) as solicitudes, AVG(tiempo_respuesta) as tiempo_promedio
FROM servicios 
WHERE DATE(fecha_hora) >= TODAY() - INTERVAL 30 DAY
GROUP BY zona 
ORDER BY solicitudes DESC

CREATE TABLE users_roles (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT UNIQUE NOT NULL,
  role TEXT CHECK (role IN ('operadora', 'contadora', 'admin')),
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE operadoras (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users_roles(id),
  nombre TEXT,
  fecha_ingreso TIMESTAMP
);

CREATE TABLE choferes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  nombre TEXT NOT NULL,
  ci TEXT UNIQUE,
  telefono TEXT,
  fecha_ingreso TIMESTAMP,
  es_socio BOOLEAN DEFAULT false,
  estado TEXT DEFAULT 'activo'
);

CREATE TABLE clientes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  numero_whatsapp TEXT UNIQUE NOT NULL,
  nombre TEXT,
  zona TEXT,
  historial_servicios INT DEFAULT 0,
  blacklist BOOLEAN DEFAULT false,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE servicios (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  cliente_id UUID REFERENCES clientes(id),
  chofer_id UUID REFERENCES choferes(id),
  operadora_id UUID REFERENCES operadoras(id),
  fecha_hora TIMESTAMP NOT NULL,
  zona TEXT,
  gps_lat FLOAT,
  gps_lng FLOAT,
  estado TEXT DEFAULT 'pendiente',
  tiempo_respuesta INT, -- en minutos
  monto DECIMAL(10,2),
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE cobros (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  chofer_id UUID REFERENCES choferes(id),
  operadora_id UUID REFERENCES operadoras(id),
  concepto TEXT,
  monto DECIMAL(10,2),
  fecha_hora TIMESTAMP DEFAULT NOW()
);

CREATE TABLE documentos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  chofer_id UUID REFERENCES choferes(id),
  tipo TEXT,
  fecha_emision DATE,
  fecha_vencimiento DATE,
  archivo_url TEXT,
  estado TEXT DEFAULT 'valido'
);

CREATE TABLE turnos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  operadora_id UUID REFERENCES operadoras(id),
  fecha DATE NOT NULL,
  hora_inicio TIME,
  hora_fin TIME,
  estado TEXT DEFAULT 'activo',
  resumen JSONB, -- guarda estadísticas
  created_at TIMESTAMP DEFAULT NOW()
);

8. SEGURIDAD Y AUTENTICACIÓN
═══════════════════════════════════════════════════════════════════════════════════════════════════════

PRINCIPIOS DE SEGURIDAD
───────────────────────

1. NUNCA guardes contraseñas en texto
   → Usa hash (bcrypt, Argon2)

2. NUNCA envíes credenciales por URLs
   → Usa POST + HTTPS

3. NUNCA guardes datos sensibles en localStorage
   → Usa httpOnly cookies para tokens

4. VALIDAR SIEMPRE en el backend
   → El frontend puede ser bypasseado

5. ENCRIPTAR datos sensibles
   → Números de CI, tarjetas, etc.

6. LIMITAR acceso por rol
   → Operadora no ve datos de contadora

7. AUDITORÍA de cambios
   → Quién cambió qué, cuándo

8. BACKUPS automáticos
   → En caso de pérdida de datos

FLUJO DE AUTENTICACIÓN (Firebase + Backend)
────────────────────────────────────────────

1. Usuario ingresa email y password en login
                │
                ▼
2. Firebase Auth valida credenciales
   (firebase.com maneja hashing, 2FA, etc.)
                │
                ▼
3. Firebase devuelve token JWT al frontend
   (token = prueba de que es válido)
                │
                ▼
4. Frontend guarda token en localStorage
   (temporalmente, para usar en API calls)
                │
                ▼
5. Frontend hace request al backend:
   GET /api/user/role
   Header: Authorization: Bearer {token}
                │
                ▼
6. Backend valida el token con Firebase
   (verifica: ¿este token es legítimo?)
                │
                ▼
7. Backend busca en Supabase el rol del usuario
   (SELECT role FROM users WHERE email = ...)
                │
                ▼
8. Backend devuelve rol al frontend
   Response: { role: 'operadora' }
                │
                ▼
9. Frontend redirige a /dashboard/operadora
   (mostrando solo lo que puede ver)

AUTORIZACIÓN POR ROL
────────────────────

Operadora puede:
✓ Ver panel de servicios
✓ Crear servicios
✓ Registrar cobros
✓ Cerrar turno
✗ NO ver datos financieros totales
✗ NO crear usuarios
✗ NO eliminar datos

Contadora puede:
✓ Ver reportes financieros
✓ Buscar cobros por período
✓ Exportar datos
✗ NO crear servicios
✗ NO ver datos operativos
✗ NO crear usuarios

Admin puede:
✓ VER TODO
✓ CREAR usuarios
✓ BORRAR datos (con cuidado)
✓ Cambiar roles
✓ Ver auditoría
✓ Configurar sistema

IMPLEMENTACIÓN EN BACKEND
─────────────────────────

middleware/verifyRole.js:

  const verifyRole = (requiredRole) => {
    return async (req, res, next) => {
      try {
        const token = req.headers.authorization?.split(' ')[1]
        
        // Verificar token con Firebase
        const decodedToken = await admin.auth().verifyIdToken(token)
        
        // Buscar rol en Supabase
        const { data } = await supabase
          .from('users_roles')
          .select('role')
          .eq('email', decodedToken.email)
          .single()
        
        // Verificar si tiene el rol requerido
        if (data.role !== requiredRole && data.role !== 'admin') {
          return res.status(403).json({ error: 'No autorizado' })
        }
        
        req.user = { email: decodedToken.email, role: data.role }
        next()
      } catch (error) {
        res.status(401).json({ error: 'Token inválido' })
      }
    }
  }

Uso en rutas:

  app.post('/api/cobros', verifyRole('operadora'), (req, res) => {
    // Solo operadoras pueden registrar cobros
  })
  
  app.get('/api/reportes/financiero', verifyRole('contadora'), (req, res) => {
    // Solo contadora puede ver reportes
  })

PROTECCIÓN DE DATOS SENSIBLES
──────────────────────────────

1. Variables de entorno
   .env nunca en git
   └─ usa .env.example

2. Encriptación de campos
   ci_encriptado = encrypt(ci)
   └─ desencriptar solo cuando sea necesario

3. Logs seguros
   NO loguear: passwords, tokens, CI
   SÍ loguear: qué hizo, cuándo, quién

4. HTTPS siempre
   En desarrollo: http://localhost:3000 ok
   En producción: HTTPS obligatorio

5. CORS configurado
   Só permitir frontend específico
   No: "*" (abierto a todos)

6. SQL Injection prevention
   NUNCA: db.query("SELECT * FROM users WHERE id = " + id)
   SÍ:   db.query("SELECT * FROM users WHERE id = ?", [id])

   Si hay error, ver qué pasó

   Dashboard → Metrics
   Ver: CPU, memoria, requests
